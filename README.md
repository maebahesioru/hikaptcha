# ヒカマニCAPTCHA

hikabooru([hikabooru.hikamers.app](https://hikabooru.hikamers.app))の**実在画像**で出題する多層認証CAPTCHA。
「◯◯の画像を全部選んで」の画像認証に、メモリハードPoW・ハニーポット・サーバー観測シグナル・
チケット束縛・画像改変を重ねる。Node 18+ のみ(ffmpegは任意。無ければ画像改変だけ無効)。

## 起動

```bash
node server.mjs                        # http://localhost:3107
PORT=8080 node server.mjs
POW_BITS=7 POW_N=2048 node server.mjs  # 計算認証を重くする
IMG_TRANSFORM=0 node server.mjs        # 画像改変を無効化(ffmpeg不要)
MIN_SOLVE_MS=1500 node server.mjs      # サーバー実測の下限
```

動作確認ページ: `http://localhost:3107/`
ドキュメントページ: `http://localhost:3107/docs`(このREADME.mdをその場でHTMLにして配信している。
手書きのdocを別に持つと必ず食い違うので、READMEが唯一の情報源)

`tools/api_walkthrough.mjs` を使うと、**下に書いてある全リクエストを実際に投げて応答を表示する**
(ドキュメントの例はこのスクリプトで取った実物):

```bash
node tools/api_walkthrough.mjs http://localhost:3108   # 正解付きのデバッグコピー
```

## 使い方(クイックスタート)

### 1. CAPTCHAサーバーを立てる

```bash
node server.mjs          # http://localhost:3107
```

### 2. サイトに埋め込む(フロント側)

```html
<div id="captcha"></div>
<script src="https://CAPTCHAサーバーのURL/captcha.js"></script>
<script>
  HikamaniCaptcha.render(document.getElementById("captcha"), {
    apiBase: "https://CAPTCHAサーバーのURL",
    // 解けた瞬間に呼ばれる。この時点ではまだ「未検証」
    onSolved: function (token, ticket) {
      fetch("/register", {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ token: token, ticket: ticket, name: "..." /* フォームの中身 */ }),
      });
    },
  });
</script>
```

ウィジェットがやること: 出題の取得 → 9枚の表示 → 選択UI → **PoW(scrypt)を解く** → `minMs` 待ち →
`/api/verify` への送信 → 失敗時はその場で再挑戦(新しい出題を自動で取り直す)。
`captcha.js` は **Shadow DOM** の中で描画するので、埋め込み先のCSSで見た目が崩れない。

### 3. サーバー側で「消費」してから受け付ける(**必須**)

```js
// 登録・投稿を受け付ける前に、必ず consume を通す
const r = await fetch("https://CAPTCHAサーバーのURL/api/consume", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({ token, ticket }),
});
const j = await r.json();
if (!j.ok) return res.status(400).json({ error: "認証に失敗しました" });
// ここから先が「人間が通った」処理(登録・投稿など)
```

```bash
# シェルから確認する場合
curl -X POST https://CAPTCHAサーバーのURL/api/consume \
  -H "content-type: application/json" \
  -d '{"token":"...","ticket":"..."}'
# => {"ok":true}
```

⚠️ **これを忘れると認証が素通りする。** トークンは**使い切り**なので、一度消費したトークンは
2回目で必ず失敗する(保存して使い回すことはできない)。トークンの有効期限は**5分**。

⚠️ **クライアントの表示だけで「認証済み」にしない。** `onSolved` が呼ばれた時点は「未検証」で、
本当の認証は**あなたのサーバーが `/api/consume` に成功した時点**で成立する。
クライアント側の表示だけで通すと、トークンを消費せずに登録できてしまう。

## 認証フロー

```
ブラウザ                         CAPTCHAサーバー                 あなたのサーバー
  │ ①GET /api/challenge ──────────▶ 出題を作る(画像9枚+PoW課題+チケット)
  │ ◀── tiles[9] / pow / ticket / minMs
  │ ②GET /api/img/<id> ×9 ───────▶ 画像を配信(**取得したことを記録**)
  │ ③人が画像を選ぶ
  │ ④scryptでPoWを解く(実測 100〜300ms)
  │ ⑤minMs まで待つ(人が見る時間の下限。ウィジェットが実装済み)
  │ ⑥POST /api/verify ───────────▶ 全層を検証(下表)
  │ ◀── {ok:true, token, risk, serverElapsedMs, imagesFetched}
  │                                                         │
  │ ⑦POST /register {token,ticket} ───────────────────────▶ ⑧POST /api/consume ─▶ CAPTCHA
  │                                                         │ ◀── {ok:true}(ワンタイム)
  │ ◀──────── 登録完了(ここで初めて「人間」とみなす)
```

⚠️ **⑦で `ticket` も一緒に送る必要がある。** トークンは発行時のチケットに束縛されていて、
チケットが一致しないと消費できない(=他人のトークンを拾っても使えない)。

| # | `/api/verify` で確認していること | 通らないと |
|---|---|---|
| 1 | 選択した画像が正解と完全一致 | 400(残り試行を返す)/ 3回で410 |
| 2 | **画像が実際に配信されたか**(未取得ならボット) | 400 `画像が読み込まれていません` |
| 3 | **実測時間**(チャレンジ発行〜回答到達) | 400 `回答が速すぎます` |
| 4 | PoWのnonceが正しいか(scrypt) | 410 `認証に失敗しました` |
| 5 | チケットが有効か | 410 `認証セッションが無効です` |
| 6 | ハニーポット欄が空か | 400 `自動入力を検出しました` |
| 7 | 挙動シグナル(操作の有無・移動量) | 通るが `risk` が上がる(ソフト) |
| 8 | 申告した所要時間と実測の整合 | 400 `申告値と実測値が一致しません` |

`risk` は加点方式の**ソフトな指標**(0〜6程度)。埋め込み先で「risк 3以上は手動確認」のように
使えるが、**判定は必須ではない**(通過の可否は上記1〜8で決まる)。

## APIリファレンス

すべて `Content-Type: application/json`。`/api/*` には CORS ヘッダ
(`Access-Control-Allow-Origin: *`)が付き、`OPTIONS` プリフライトにも応答する。

### GET /api/challenge

出題を1件作る。パラメータは無し。**本番は正解(`target`)を返さない**(デバッグコピーのみ付く)。

```bash
curl -s http://localhost:3107/api/challenge
```

実際の応答(デバッグコピーで正解を可視化したもの):

```json
{
  "id": "056ae9330ba4f6e6",
  "mode": "or",
  "ask": {
    "mode": "or",
    "tags": ["ボディスーツ", "上着"],
    "n": 0,
    "maxSelect": 0,
    "text": "「ボディスーツ」または「上着」が写っている画像を全部選んでください"
  },
  "tags": ["ボディスーツ", "上着"],
  "prompt": "「ボディスーツ」または「上着」が写っている画像を全部選んでください",
  "tiles": [
    { "id": "cc8d38f9a970", "url": "http://localhost:3108/api/img/87e109dd625070e75935c5b8" }
  ],
  "ticket": "75d0ef125e92...(48字)",
  "pow": { "algo": "scrypt", "challenge": "ee27257df6cd...(32字)", "salt": "7dbbd3117261...(32字)",
           "bits": 6, "N": 1024, "r": 8, "p": 1 },
  "honeypot": "website",
  "minMs": 1500
}
```

| フィールド | 説明 |
|---|---|
| `id` | 出題ID。`/api/verify` にそのまま返す |
| `ask.text` | **画面に出す文面そのもの**。サーバーが組み立てるのでクライアントで作らない |
| `ask.mode` | 6形式(`single`/`pick`/`not`/`notpick`/`or`/`and`) |
| `ask.tags` | お題のタグ(1〜2個) |
| `ask.n` | `pick`/`notpick` の枚数 |
| `ask.maxSelect` | 選べる枚数の上限。**0は無制限**(全部選ぶ形式) |
| `tiles[]` | `id` と画像URL。URLは**不透明ID**経由で元投稿は分からない |
| `ticket` | 認証セッション。消費時にも必要 |
| `pow` | scryptのパラメータ。`nonce` を探して `leadingZeroBits(scrypt(challenge+":"+nonce, salt)) >= bits` にする |
| `honeypot` | 人間には見えない入力欄の `name`(ここでは `website`)。**記入されたら即ボット判定** |
| `minMs` | 回答を送るまでの下限。これを待たずに送ると `回答が速すぎます` になる |

⚠️ 同一IPで保持する出題は**最大10件**で、超えると古いものから捨てられる(別タブ・NAT対策)。

### GET /api/img/<imgId>

画像プロキシ。配信時に長辺640pxへ縮小+3:2へ整形+再圧縮したものを返す(`cache-control: no-store`)。
**「誰がどの画像を見たか」をサーバーが記録していて、1枚も取得していない回答は拒否される。**

### POST /api/verify

```bash
curl -X POST http://localhost:3107/api/verify -H "content-type: application/json" -d '{
  "id": "056ae9330ba4f6e6",
  "selected": ["cc8d38f9a970", "61635834b910"],
  "ticket": "75d0ef125e92...",
  "nonce": "127",
  "elapsedMs": 2677,
  "signals": { "interactionSeen": true, "pointerMoves": 24, "clicks": 2, "touchSeen": false, "powMs": 286 }
}'
```

成功(実物):

```json
{ "ok": true, "token": "6a827406145deca2b3ff94fb54c9fd4ecb4e3178cc897805", "risk": 0,
  "serverElapsedMs": 2677, "imagesFetched": 9 }
```

| リクエスト | 説明 |
|---|---|
| `selected[]` | 選んだタイルの `id`。**過不足なく**一致しないと不正解 |
| `nonce` | PoWの解(文字列) |
| `elapsedMs` | クライアントが測った所要時間(実測と大きく食い違うと拒否) |
| `signals.interactionSeen` | 操作が観測されたか(クリック/ポインタ/キー) |
| `signals.pointerMoves` | ポインタ移動の回数 |
| `signals.touchSeen` | タッチ操作だったか(移動量の判定を緩める) |
| `signals.touchedHidden` | 隠し要素に触れたか(**触れたら減点**) |
| `signals.powMs` | PoWに要した時間 |
| `website` | ハニーポット(`challenge.honeypot` の名前で送る)。**空で送る** |

| レスポンス | 説明 |
|---|---|
| `token` | ワンタイム解決トークン(48字)。`/api/consume` に渡す |
| `risk` | ソフトなリスク値(0=きれい) |
| `serverElapsedMs` | サーバー実測の所要時間 |
| `imagesFetched` | 実際に取得された画像の枚数 |

### POST /api/consume

**あなたのサーバーから呼ぶ**(ブラウザから直接でもよいが、判定はサーバー側で完結させること)。

```json
{ "ok": true }
```

### GET /api/health

```json
{ "ok": true, "stats": { "challenges": 12, "tagRejects": 5, "modes": {"single": 7}, "relatedPromoted": 2 } }
```

`stats` には出題数・フィルタの却下数・形式の内訳・空振り理由(`fShortBatch` 等)が入る。
**「出題が遅い/出ない」を調べるのはまずここ。**

## エラー一覧(実際に返るメッセージ)

| ステータス | メッセージ | 意味 |
|---|---|---|
| 400 | 違う画像が混ざっています(あとN回)。選び直してください | 選択が不正解。`remaining` に残り試行 |
| 400 | 自動入力を検出しました。最初からやり直してください | ハニーポットに記入された(ボット) |
| 400 | 画像が読み込まれていません。ページを再読み込みしてもう一度お試しください | 画像を1枚も取らずに回答した |
| 400 | 回答が速すぎます。もう一度やり直してください | 実測が `HARD_MIN_SOLVE_MS` 未満 |
| 400 | 申告値と実測値が一致しません。もう一度やり直してください | `elapsedMs` の申告が実測と大きく違う |
| 400 | トークンがありません / トークンが無効です(期限切れ or 使用済み) | consumeの失敗(未指定・消費済み) |
| 400 | トークンの期限が切れています | トークンの5分TTL切れ |
| 400 | トークンと認証セッションが一致しません | チケット不一致(横流し) |
| 410 | 不正解です。新しい問題に挑戦してください | 3回失敗して出題を破棄 |
| 410 | 出題が見つかりません。もう一度やり直してください | 出題IDが無効(破棄済み・未発行) |
| 410 | 出題の期限が切れました。もう一度やり直してください | 出題のTTL切れ |
| 410 | 認証セッションが無効です。もう一度やり直してください | チケットが無効 |
| 429 | リクエストが多すぎます。あと約N秒で再開できます | レート制限(**既定は無効**=`IP_QUOTA=0`) |
| 502 | 問題を準備できませんでした。少し待ってからもう一度お試しください | 出題生成の連続失敗(時間をおく) |

`410` は「その出題はもう使えない」の意味なので、**クライアントは新しい出題を取り直す**こと
(同梱のウィジェットは自動でそうする)。

## トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| **認証が素通りする** | `/api/consume` を呼んでいない。呼ばないとトークンは永遠に有効なまま(5分) |
| 毎回 `回答が速すぎます` | ウィジェットを使わず自前実装している。`minMs` を待ってから送る |
| 毎回 `画像が読み込まれていません` | タイル画像を取得せずに `/api/verify` を叩いている(取得が必須) |
| `429` が返る | `IP_QUOTA` を設定した時だけ出る。既定(0)では出ない |
| 埋め込み先で見た目が崩れる | `captcha.js` は Shadow DOM で隔離しているので、通常は影響しない。`apiBase` の指定漏れを確認 |
| 出題が返らない・遅い | `/api/health` の `stats` を見る(`fShortBatch` 等の空振り理由) |
| 出題形式を固定して試したい | `FORCE_MODE=single node server.mjs` |
| 正解を見ながら試したい | `python tools/make_debug_copy.py` → `PORT=3108 node <コピー先>/server.mjs`(正解付き) |

## 認証の層

| 層 | 内容 | 何を防ぐか | 実測 |
|---|---|---|---|
| 1. 画像認証 | hikabooruの9枚から条件に合う画像を全部選ぶ(単一タグ or 2タグAND) | 内容理解の要求 | — |
| 2. メモリハードPoW | scrypt(N=1024,r=8)出力の先頭ゼロビット探索を回答前に要求 | 量産・GPU突破の単価を上げる | sha256比 **1試行あたり約780倍**のコスト |
| 3. 画像改変 | 配信時に長辺640pxへ縮小+微小ガンマ+再圧縮(クロップ・反転・回転は廃止) | バイト一致 | バイト一致は回避(知覚索引には無力 → 下記参照) |
| 4. 画像取得の実測 | 画像が実際に配信されたかをサーバーが記録し、未取得なら拒否 | 画像を見ないスクリプトの直叩き | 未取得は **拒否** |
| 5. 実測時間 | チャレンジ発行〜回答到達をサーバー時計で測り下限を強制 | 高速ソルバーの即答 | 即答は **拒否** |
| 6. チケット束縛 | 解決トークンを発行時のチケットへ固定、消費時に一致必須 | トークンの転売・横流し | 別チケットの消費は **拒否** |
| 7. 仕事量予算 | IPごとの累計PoW仕事量に上限(**既定オフ**) | 計算資源による総当たりの速度制限 | `IP_WORK_BUDGET` を入れた時だけ働く |
| 8. ハニーポット | 人間に見えない入力欄 | フォーム自動入力型のボット | 記入は **即拒否** |
| 9. 適応難易度 | 突破実績の多いIPはPoWを段階的に強化 | 継続的な突破 | 3回突破で 6bit→7bit |
| 10. 挙動シグナル | 操作の有無・移動量・所要時間(補助) | 安価なボット | 操作ゼロは追加の減点 |

さらに:
- 画像URLは自前プロキシ(`/api/img/<不透明ID>`)経由。元の投稿IDを出さない
- **レート制限とクォータは既定で無効**(無制限)。仕組みは残してあり `IP_QUOTA` を入れれば効く
- 同一IPの出題は最大10件保持し、超えた分は古いものから捨てる(別タブ・NATで壊れない。これは流量制限ではなくメモリ保護)
- 1件の失敗でサービス全体が落ちないよう unhandledRejection / uncaughtException をガード

## 出題の仕組み(方式は固定・除外の根拠を実測で強化)

方式は「**ランダム画像バッチ + 除外フィルタ**」で固定。お題タグは1つに限らず、**出題形式も6種類**ある。

1. hikabooruのsafe画像を**ランダムなoffset位置**から取得(出題のバラエティを担保)
2. 条件を満たすタグを探し、形式に応じて正解とダミーを構成する
3. 正解情報はサーバー側のみ保持。クライアントへは画像URLと不透明IDのみ

### 出題形式(6種類)

形式 = **{タグを持つ | 持たない} × {全部 | N枚だけ}** と、2タグの AND / OR。

| mode | 文面 | 正解 | 実測(1件=visionに同じ9枚を見せて真実と突き合わせ) |
|---|---|---|---|
| `single` | 「◯◯」の画像を全部選べ | タグを持つ画像 | 従来の基準形式。タグの誤りが1つあると1枚ずれる |
| `pick` | 「◯◯」が写っている画像を**N枚だけ**選べ | タグを持つ画像からN枚 | **実測3件すべてで1枚ずれ**。枚数固定なのでタグ1つの誤りが即不正解 |
| `not` | 「◯◯」が写ってい**ない**画像を全部選べ | タグを持たない画像 | **実測2件で良好**(8/8一致、7/8+ダミーを正しく指摘)。ダミー1枚を探す形は人間に明確 |
| `notpick` | 「◯◯」が写っていない画像を**N枚だけ**選べ | タグを持たない画像からN枚 | 実測2件で完全一致1・1枚ずれ1(仲間外れとして視覚的に分かりやすい) |
| `or` | 「◯◯」または「△△」が写っている画像を全部選べ | どちらかを持つ画像 | 実測3件すべてで余分な正解が出た(ダミーが2タグ両方を持たない必要があり誤漏れに弱い) |
| `and` | 「◯◯」と「△△」の**両方**が写っている画像を全部選べ | 両方を持つ画像 | **実測4件すべて失敗**(AIタグ付けでは両方写っている画像がほぼ無い) |

既定の重みは実測に基づく: `single=3,not=3,notpick=1,pick=1,or=1,and=0`
(`MODE_WEIGHTS` で変更可。`FORCE_MODE` で検証時に形式を固定できる)

**なぜ `and` は0なのか**: 正解は「両方のタグを持つ画像」= AIが2つとも正しく付けた画像に限られる。
実測では真実2枚に対しvisionが7枚該当と判定する(誤漏れ5枚)など、成立しなかった。
**解けないCAPTCHAはロボットより人間を弾く**ので既定では出さない。

形式ごとの共通の限界: どの形式も**タグと画像の対応**に依存するため、AIタグの誤付与/誤漏れが
そのまま不正解になる。特に「◯枚だけ」系は枚数が固定なので1つの誤りが致命的、`or` は
ダミーが2語とも持たない必要があるため誤漏れに弱い。逆に `not` 系はダミー1枚を探す形なので最も安定した。

### 出題生成の性能(実測して直した)

形式を増やした直後は**出題が遅くなった**(中央値2.2秒・試行4.3回/件)。`/api/health` の
失敗理由カウンタで原因を特定して直した:

| 実測した原因 | 対策 | 結果 |
|---|---|---|
| **フィルタ通過率が低い**: ランダム取得20枚では段階0のフィルタ通過が9枚に足りない(実測: limit30で通過 中央値5枚=**80%が空振り**、limit60なら中央値10枚=20%) | 取得枚数を60にし、足りない時は100枚で取り直す | 空振り 66→22 |
| **候補タグの枯れ**: 「タグがちょうどN枚に付いている」を条件にしていたため、取得枚数を増やすと候補が消えた | グリッドに出す枚数はこちらで選べるので「タグを持つ画像がN枚以上ある」に緩和 | 空振り(`fNoTag`)が減少 |
| **`not` の構成崩れ**: 一貫性フィルタが正解を削り、ダミー枚数と辻褄が合わなくなっていた(実測 `fPool` 10件) | not / notpick では一貫性フィルタをスキップ | 緩和レベルへの流出が減った |

結果(本番25回連続・実測): **出題 25/25成功 / 中央値 1142ms / 試行 2.6回/件 / 緩和0件**
= 品質フィルタを1件も緩めずに出題できている。


### タグの除外(実測9周 + 辞書の品詞判定)

お題に使えるのは「画像を見て判別できる具体物」だけ。除外の根拠:

- **構造ルール**: 記号・約物を含む(●_豆獣石× / 野菜、野菜 / 靴…)※「・」はカタカナブロック内なので個別対応
- **構造ルール**: 数字入り・空白入り・括弧付き・助詞入り(を/が)・「の」入り(説明文になる)・抽象語尾(化/型/的/者/員/類)
- **辞書(UniDic)による品詞除外** (`tag_reject.json` / `tools/build_pos_reject.py` が生成):
  形状詞(必要/シュール/コミカル)・サ変可能な名詞(キャンセル/退出/制作)・固有名詞の地名/人名(東京/仙台/浜口)
  = 画像を見て判別できない語を機械的に **455件**除外
- **実測ブラックリスト**: サンプル点検で見つけた不正タグを9周にわたって追加
- **具体性の重み付け**: 使用回数が多いタグ(=ありふれた具体物)ほど選ばれやすくする

### レート制限(現在は既定で無効)

**いまは無制限**(`IP_QUOTA=0`)。自分の用途では制限が要らないため既定で外してある。
仕組み自体は残してあり、`IP_QUOTA` を入れれば効く。以下はそこに至るまでの実測ログ。

**症状**: 自分で試している最中に「リクエストが多すぎます。しばらく待ってから再試行してください」が出て、
最大10分待たされる。原因は**固定窓**方式(10分で60回、超えたら窓が終わるまで全拒否)だった。

直したこと:

1. **トークンバケット方式**にした。使った分が少しずつ回復するので崖がない
   (既定: 同時100 + 3秒ごとに1個回復 = 持続20回/分)。超過時は `retryAfterMs` / `Retry-After` を返す
2. **ローカル/プライベートIPは制限しない**(開発・検証で自分が詰まらないため)。
   ただし `X-Forwarded-For` が付いている場合は除外しない
   → 本番でリバースプロキシ越しに来る外部アクセスには効いたまま
3. **待ち時間を必ず伝える**。文言も「あと約N秒で再開できます」に統一し、
   ウィジェットは**カウントダウン表示→自動で取り直す**(エラー文字列を出して終わりにしない)
4. **出題生成の同時実行を制限**(既定4、キュー32)。無制限に並走させると
   booru API と ffmpeg で自分のリソースが詰まり 502 が多発する
   (実測: 同時130発で68件が502 → 制限後は 200×36 / 429×94 で502ゼロ)
5. **適応難易度もローカルでは上げない**(検証中にPoWが重くならないように)

実測:
```
ローカル 200回連続 → 200/200 成功(429なし)
外部IP 同時130発   → 200×36 / 429×94(「あと約3秒で再開できます」) / 502ゼロ
ウィジェット実測(実時間/CDP) → 待機表示「あと5秒で自動的に再開します」→ 自動で出題に復帰
```

### 制限を外した後の実測(現在の既定)

既定で無制限にしたうえで、同じ負荷をかけて確認した:

```
ローカル 50回連続       → 50/50 成功
外部IP 同時130発        → 130/130 成功(429ゼロ・502ゼロ) / 所要 80秒
```

つまり**拒否は一切しない**。負荷が来たときは「エラーで弾く」のではなく
「時間がかかる」方向に倒れる(同時実行だけ4に絞って順番待ちは無制限にしたため)。

制限を戻したいときは `IP_QUOTA=100` のように入れる(有効化できることは実測済み:
`IP_QUOTA=3` で3成功/3拒否、`/api/health` の `stats.lastQuota` に判定したIPが出る)。

⚠️ 副産物: この改修中に **`checkQuota` のリファクタで `ip` 未定義のバグを混入**させ、
「ローカル以外(=本番で一番重要な経路)だけ500になる」状態を作った。
ローカルIPは免除でその行に到達しないため気づきにくかった。
→ **免除を入れたら、免除されない経路(外部IP相当)を必ずテストする**。
テストスイートも `X-Forwarded-For` を付けて外部クライアントを装うようにした。

### 「全部の画像がなんとなく似通ってる」の原因と修正(実測)

ユーザー指摘から調査したら、**方式のバグ**だった。1回の連続取得(`limit=60&offset=N`)は
その60件が**投稿IDの連番の塊**(間隔平均1.0)=アップロード順のひとかたまりで、
hikabooruでは同じ投稿者が大量に連投しているため、**9枚すべてが同じ投稿者の画像**になっていた。

実測(`SAMPLES_PER_BATCH=1` の旧挙動 vs `=6` の改善版、各12件):

| 指標 | 旧(連続取得) | 新(6箇所から小分け取得) |
|---|---|---|
| 9枚のうち同じ投稿者の最大枚数 | **9.0枚**(全件で9枚) | **2.9枚** |
| 9枚に含まれる投稿者の種類 | **1.0種** | **5.2種** |
| 投稿IDの間隔(平均) | 7.8 | 3052 |
| 9枚の画像類似の平均距離(64bit) | 28.7 | **30.9** |
| 最も似ているペアの距離 | 0〜7(ほぼ同一画像が並ぶ) | 18以上 |

やったこと:

1. **複数の離れたoffsetから小分けに取得**(`SAMPLES_PER_BATCH=6`)。並列取得なので速度は落ちない
2. **投稿者ごとに1枚ずつ巡回して選ぶ**(ラウンドロビン)。正解・ダミーの両方に適用
3. **同一画像の混入を却下**: グリッド内の2枚がほぼ同一(署名距離≦2)なら捨てる
   (同じ絵なのに片方だけ正解/不正解になるのは不公平)

結果: 出題 25/25成功 / 中央値 **899ms** / 試行 2.4回/件(速度はむしろ改善)

⚠️ 残る限界: hikabooru自体の構成に偏りがあり(**投稿元の83%がx.com**、別の集計で**37%がサムネイル系タグ**。同じ画像を別の軸で数えた値なので合計は100%にならない)、
「同じYouTuberの別動画のサムネイル」という意味での類似は残る(実測でvisionもそう指摘)。
これは元データ側の性質で、取得方法では解消できない。

### 画像の見え方(visionで実測しながら改善)

見づらさの原因を順に潰した(すべてvisionで実際のタイルを見て確認):

| 症状 | 原因(実測) | 対策 |
|---|---|---|
| タイルが小さい・黒帯 | 正方形タイル+containで横長画像の上下40%が余白(被写体が面積46%) | タイルを**3:2**にし、余白は**同じ画像のぼかし**で埋める(黒帯を出さない) |
| 被写体が端で切れる | 3:2へクロップしていた。3:2に近い画像は全体の**2.8%**しかなく、無理なクロップが切れを生む | **クロップを廃止**(contain配信で全体を見せる) |
| 鏡像・黒い三角 | 反転(50%)と回転をかけていた。日本語が逆さになり、回転で黒い角が出る | **反転・回転を廃止**(反転は適応的攻撃者に距離0.2で無効という実測もある) |

### タグの精度(実測で原因を特定して改善)

お題タグの不正率は約60%→**約13%**(名前の段階)。ただし本当の問題は**タグと画像の対応**だった:

- **スクリーンショット画像**: 安全画像の約**51%**がスクリーンショット系タグ付き(最多は「日本語のテキスト」)。
  こうした画像はお題の被写体が「画面の小さなアバター」で、タグは正しくても人間には判定不能
  → **スクリーンショット系タグの画像をプールから除外**
- **AIタグの誤付与**: 実測で「バッグ」の正解に**電車の画像**が含まれていた(正解が人間に見て分からない)
  → 出現回数の多いタグ(=その画像の主題)を優先し、**3枚以上に付くタグ**を基本にする
- **誤付与された孤立画像**: 商品の箱だけの画像に「カーディガン」が付く等、他の正解と共通タグを持たない
  → **正解候補同士が共通タグを持つ組だけを正解にする**(一貫性フィルタ)

この結果、visionによる独立判定が真実と一致するようになった(実測: 「カービー」で上中・右下の2枚が正解、visionも同じ2枚と回答)。

#### さらに踏み込んだ改善(実測で特定した2つの失敗型)

visionで実際の出題を採点すると、次の2つの型の不公平が見つかった。どちらも**方式(ランダムバッチ+ブラックリスト)は変えずに**フィルタを足して潰した。

| 失敗型 | 実測例 | 原因 | 対策 |
|---|---|---|---|
| **ダミーが正解と同じに見える** | 「青いシャツ」: 真実2枚に対しvisionは**7枚**を該当と判定 | 同じキャラの紺Tシャツ9枚のうちタグが2枚にしか付いていない(付与の不整合)。人間には区別できない | **見分けやすさフィルタ**: 正解同士のタグ類似度とダミーの類似度を比較し、ダミーが正解と同程度に似ている出題を捨てる(実測で不公平な出題 **20% → 0%**) |
| **ダミーが画像として似すぎている** | 「長袖」: 真実2枚に対しvisionは**8枚**を該当と判定 | 同じ人物の雪山ジャケット連続写真。タグの重なりでは検出できない | **視覚フィルタ**: 画像を8x8グレースケールの64bit署名にし、ダミーが正解と見分け不能な出題を捨てる(依存ゼロ。1回のffmpegで9枚まとめて処理) |

さらに実測で分かった2点:

- **一貫性フィルタの落とし穴を修正**: ゴミタグ(`11` / `なんだって` / `おじいちゃん向けコンテンツ` 等)はほぼ全画像に付くため、それを「共通タグ」として数えるとフィルタが無効化していた。お題タグと同じ基準を通る**意味のあるタグだけ**で判定するようにした。
- **2タグAND出題は既定で無効**: vision検証4件すべてで成立しなかった(「ビーニー×野球帽」→真実2枚にvisionは7枚、「ジュースボックス×モグラ」→真実2枚ともvisionは「該当なし」)。AIタグの誤付与どうしの重なりで作られるため、両方が本当に写っている画像はほぼ無い。解けないCAPTCHAはロボットより人間を弾くので `PAIR_PROB` の既定を **0** にした(環境変数で有効化可)。
- **素材・抽象語をお題から除外**: 「ガラス」は真実2枚に対しvisionが5枚を該当と判定した(水槽・窓・テレビ画面・瓶まで拾う)。付随的に写る素材語(ガラス/透明/金属/布/光/影/文字/ロゴ 等)はお題にしない。

#### 品質フィルタの統計(チューニング用)

`/api/health` がフィルタの効き具合を返す。実測(40回連続出題):

```
出題 成功 40/40 / 中央値 1247ms / p90 1666ms
challenges: 40, tagRejects: 8, visRejects: 5, relaxedUsed: 11
```

閾値を厳しくしすぎると大半の出題が弾かれ、緩和レベル(品質フィルタOFF)に流出して**実質無効**になる
(実測: 視覚フィルタの閾値を0.9にすると却下94%・緩和レベルに22/30が流出)。そのため
「明らかに不公平な場合だけ落とす」控えめな閾値にし、却下のたびに段階的に緩めて**可用性を必ず確保**している。


#### タグの誤りを「サイト全体の統計」で補正する(共起タグ)

AIタグの誤付与(電車の画像に「バッグ」)と誤漏れ(カーディガンを着ているのにタグが無い)は、
**画像の中身を見ないと分からない**。ここで使えるのが hikabooru 自身の統計:

> 「タグTが付いた画像群に共通して現れる珍しいタグ」= Tらしい文脈。
> その文脈を持っているのに T が付いていない画像は、**Tが写っているのに付け忘れられている**可能性が高い。

実装(`getCompanions`): T付き画像を60枚取って共起タグを集め、IDF(珍しさ)で重み付けする。
タグ1個につき1回だけ取得して10分キャッシュするので、出題あたりの追加コストは小さい。

**visionによる決定的な検証(眼鏡で実測)**:

| 群 | 何を検出したいか | 実際に眼鏡が写っていた枚数 |
|---|---|---|
| タグ無し + 共起スコア上位6枚 | **誤漏れ** | **5/6枚** |
| タグ有り + 共起スコア0の6枚 | **誤付与** | 写っていなかったのが **4/6枚** |

つまりこのスコアは「画像にTが写っているか」を実際に予測している。使い方は**閾値ではなく順位**:

- **ダミーはスコアの低い順から選ぶ**(「写っていない」確度が高い画像を優先する) ← 誤漏れ対策の本命
- **正解はスコアの高い順から選ぶ** / タグ無しでもスコアが高い画像は**正解側に昇格**(誤漏れの救済)
- スコア0(=そのタグの文脈が皆無)のタグ付き画像だけは、正解が2枚以上残る場合に限って除外(誤付与)

**実測(9枚中の誤りタイル率。モード構成に依存しない指標)**:

```
修正前                    18.5%   (誤付与12.0% / 誤漏れ20.5%)
関連タグの昇格のみ        14.8%   (誤付与11.1% / 誤漏れ16.0%)
共起スコアを閾値で使用    16.7%   (誤付与21.1% / 誤漏れ15.7%)
共起スコアを順位で使用    16.7%   (誤付与12.0% / 誤漏れ18.1%)  ← 採用(完全一致は 6/12 で最良)
```

⚠️ **正直に**: 12件ずつの比較なので、この差(1〜3枚/108タイル)は**誤差の範囲**。
「効いている」と言い切れるのは上の決定的検証(5/6・4/6)のほうで、
出題全体の改善は数%レベルにとどまる。支配的な残り誤差は**誤漏れ**(タグの付け忘れ)で、
これは統計では拾えない(そのタグの文脈を持たない画像に写っている場合)。

**やってみて効かなかったもの(再試行しない)**:

- **タグのメタデータ**: hikabooruのタグは全部 `category=default`。タグの含意・提案(implications/suggestions)も**全部空**で、人間が付けたタグとAIタグを区別する手がかりは無い
- **閾値でダミーを削る**: ダミーはグリッドの大半を埋めるため、削ると出題が作れなくなる(実測: `notpick` が `fPool` で全滅した)。**削除ではなく並べ替え**が正解
- **視覚的な分離度で不公平さを事前判定**: 「正解とダミーの見た目が離れているか」は不公平さを予測しない(分離0.97の出題が完全一致、1.10の出題が5枚ずれる)


#### 使えるタグは何個あるのか(実測: 374,884個のうち316個)

「大量にタグがあるのだから全部使えばいい」という指摘を実測で確かめた:

| 範囲 | タグ総数 | 名前フィルタ通過(お題に使える) |
|---|---|---|
| booru全体 | **374,884** | — |
| usages 150〜3000(現行の帯域) | 1,413 | **316個** |
| usages 80〜3000(下限を緩和) | 2,191 | 525個 |
| usages 150〜10000(上限を緩和) | 1,516 | 316個(増えた103個は全部メタ/ゴミ) |

つまり**374,884個の99.9%はAIノイズ**(`usages:1` のタグが大半、`れ` / `△` / `ありがとうございました` など)。
実用品質の帯域は1,413個、そこから「お題の文面として成立する語」だけを残すと**316個**になる。
これが語彙の上限で、120問で104種だから**3回に1回は同じタグが出ていた**わけではないが、
狭いプールを使い回しているのは事実だった。

**下限を80に広げる実験もした**(使えるタグは+209個):

```
                     タイル誤り率   完全一致
usages>=150(現行)      16.7%      6/12
usages>=80 (拡大)      31.9%      0/8
```

珍しいタグ(usages 80〜149)はタガーが付与を誤りやすく、**不公平な出題が倍増した**ため不採用にした。
`TAG_MIN_USAGES=80` で切り替えられる状態にはしてある(多様性を優先したい時用)。

この調査の副産物として**不適切語の混入**も見つけて直した:
現行の帯域に `多性器`(421) / `二重肛門`(437) / `セックストイ`(239) が、
80〜149の帯域に `ヌード`(98) / `セックス`(149) / `性器`(106) / `ディルドー`(91) が存在した。
**画像は safety:safe でも、CAPTCHAの文面に出る語として除外**する必要がある(実測で見つけた語をリスト化)。


#### 同じタグが繰り返し出る問題(実測: 再出率40% → 18.8%)

「なんか同じようなタグ多くね？」という指摘から実測した。**120問で延べ130回・異なり78種 = 再出率40%**、
礼服×10 / 茶髪×8 / バッグ×6 のように一部のタグに偏っていた。

原因は2つ:

1. **重みが人気タグに偏っていた**: `n² × concreteness(usages)` では「バッチに5枚あって使用回数も多いタグ」が
   他より**24倍**有利で、同じタグが繰り返し当たっていた
2. **そもそも候補が毎回ほぼ同じ**: バッチは60枚の無作為抽出だが、DBの内容が巨大シリーズに偏っているため
   「どのバッチにも出てくるタグ」が存在する。使えるタグの語彙自体が狭い

直したもの:

- **重みの平坦化**: `n^1.5 × √concreteness` にして偏りを緩めた
- **直近に出したタグを避ける**(IPごと・15分・最大200タグ): 同じタグとその類似タグ
  (「リボン / ヘアリボン」のような文字列の重なり、「金髪 / 黒髪」のような同じ末尾の漢字)を避ける
- **候補が全部直近だったときは「最後に使ってから一番古いタグ」を選ぶ**。
  ⚠️ ここで人気タグ順に戻すと茶髪×8が再発した(実測)。順番に使い回す動きにするのが正しい

結果:

```
                    異なりタグ      再出率   最多タグ
修正前(120問)        78種         40.0%   礼服×10 / 茶髪×8
途中(120問)         104種         18.8%   礼服×4  / 茶髪×4
最終(80問)          89種          3.3%   ヘアフラワー×2 / シャツ×2   ← 「一番古い候補」方式に変更後
```

**測って分かった「効果が無かった」こと**: `TAG_MIN_USAGES` を150→80に緩めても語彙は増えなかった
(75種 vs 78種)。効いている制約は「バッチ内で2枚以上に付くタグ」という条件の方で、
使用回数の下限ではなかった。

⚠️ この作業中に**500エラー(2〜3割の出題が失敗)を混入させてしまい**、A/B比較(前コミット 30/30 vs 現行 23/30)で
原因を特定した。フォールバックが `undefined` を返していた(カンマ式でMapのエントリになっていなかった)。
修正後は **40/40 成功・例外0**。

## 他サイトへの埋め込み(実測で確認済み)

`captcha.js`(ウィジェット) + `/api/consume`(トークン消費)の2つで、**別オリジンのサイトに埋め込んで
認証ゲートとして使える**。実測は `tools/embed-test/`(模擬サイト :3200 + CAPTCHA本体 :3108)で行った。

```
埋め込み検証(別オリジン): 18 PASS / 0 FAIL を3回連続
  ✅ 別オリジンから captcha.js を読んでウィジェットが描画される(タイル9枚)
  ✅ 画像を cross-origin で読み込める(/api/img に CORS ヘッダ)
  ✅ cross-origin で /api/challenge を取得できる(POSTはOPTIONSプリフライトも対応済み)
  ✅ 解いて onSolved(token, ticket) を受け取れる(トークン48字)
  ✅ トークン受領だけでは「認証済み」にしない(状態を分ける)
  ✅ 埋め込み先のブラウザ経由で consume して認証済みになる
  ✅ サーバー間でも /api/consume できる(実際のBFF)
  ✅ 同じトークンの二度使いは拒否(ワンタイム)
  ✅ チケット無しの消費は拒否(横流し対策)
```

⚠️ **クライアントだけで「認証済み」にしないこと。** トークンを受け取った時点は「未検証」で、
本当の認証は**埋め込み先のサーバーが `/api/consume` に成功した時点**で成立する。
クライアント側の表示だけで通してしまうと、トークンを消費せずに登録できてしまう(使い回せる)。

埋め込み方とサーバー側の消費のしかたは **「使い方(クイックスタート)」** を参照
(この節は「本当に別オリジンで動くのか」を実測した記録)。

### 複数サイトで使うなら足りないもの(正直に)

| 足りないもの | 現状 | 影響 |
|---|---|---|
| **サイトキー / オリジン制限** | 無し(誰でも埋め込める) | サイトを識別できないので「どのサイト向けに発行したトークンか」を区別できない。トークンの流用自体は不可能(token+ticketの両方が必要)だが、想定外のサイトに使われる |
| **サイトごとのクォータ** | 無し(IP単位のみ) | 1サイトの乱用が全サイトに影響する |
| **ハニーポットのフィールド名** | 固定(`website`) | 既知になれば回避される。サイトごとにランダム化する余地がある |
| **スケール** | 単一プロセス・メモリ保持 | 複数インスタンスにするなら状態をRedis等へ移す必要がある |

### 実測で見つけて直したバグ: 「回答が速すぎます」で正当な回答が弾かれる

埋め込み検証を回したら**3回に1回失敗**した。原因は:

- サーバーが「チャレンジ発行→回答到達」の実測が `MIN_SOLVE_MS`(1500ms)未満の回答を**ハード拒否**していた
- ウィジェットは PoW が終わった時点で即送信していて、`minMs` を待っていなかった
- **画像がブラウザキャッシュに載っている2回目以降のアクセス**や「1枚だけ選べ」のような一瞬で解ける出題で、
  正当な人間の回答が 1500ms を割って弾かれていた(実測: `serverElapsedMs: 2331` で成功する回と、
  `回答が速すぎます` で 400 になる回が混在)

直したもの:

1. **ウィジェットが `minMs` まで待ってから送信**するように(サーバーが返す `minMs` を尊重)。
   これが本質的な修正で、人間の回答は必ず下限を超えるようになる
2. サーバー側のハード拒否の下限は `HARD_MIN_SOLVE_MS` として切り出した(既定は `MIN_SOLVE_MS` と同じ)。
   カスタム実装に寛容にしたい場合だけ下げられる

補足: 下限を 700ms まで下げる案も試したが、**画像取得の所要時間が変動するため
「即答を弾く」テストが不安定になった**(取得が700msを超えると通ってしまう)。
ウィジェットが待つ契約にしたうえでサーバーは 1500ms で弾くほうが、確実で安全。

結果: 埋め込み検証が **3回連続 18/18**、多層認証テストも **3回連続 20/20** に安定。

## 残っている限界(正直なところ)

前バージョンから 4点を大幅に改善したが、**ゼロにはできていない**:

| 限界 | 状態 | 残るリスク |
|---|---|---|
| 画像認識ボット | **一部改善** | バイト一致・素朴な索引は無効化できるが、**幾何変換を列挙する適応的な攻撃者にはpHashが一致してしまう**(実測: 反転×クロップ×回転×ガンマの18通りを試すと距離は平均4.7まで縮む)。知覚ハッシュは幾何変換に頑健なため、幾何の範囲では原理的に破れない。**リアルタイムで画像分類する**ボットは当然解ける |
| クライアント申告の偽装 | **大幅改善** | 主軸を「画像が実際に配信されたか」「サーバー実測時間」に移したので偽装不能。ただし挙動シグナル自体は依然として自己申告で、単独では信用していない(補助のみ) |
| ハニーポット無効なボット | **改善** | 埋めないボットはハニーポットを素通りするが、**画像取得の実測**が代わりに捕まえる(画像を取らずに回答はできない) |
| PoWの計算突破 | **大幅改善** | sha256→scryptでメモリハード化し1試行のコストを約780倍に。さらに仕事量予算で総量を頭打ち。ただし**時間をかければ突破は可能**で、上限を消すことはできない |
| タグの精度 | **改善** | 不正タグ率は 約60% → 約13%。ただし**ゼロにはできない**(造語と実在語を辞書なしで見分けるのは原理的に困難)。実測で残るのは「リンク」「詳細」のような短い一般語 |
| 2タグ出題の公平性 | **新規** | 「両方写っている」を要求するため、AIタグ付けの取りこぼし(片方しか付いていないが視覚的には両方ある画像)があると人間でも間違えうる。片方だけ持つ画像をダミーに混ぜているぶん、この影響を受けやすい |

構造的な限界:
- **画像を実際に読む分類器には原理的に弱い**。これは画像CAPTCHA共通の限界(reCAPTCHA v2の画像課題も同様に解かれている)
- **知覚ハッシュによる索引破壊は「幾何変換の列挙」で破られる**。幾何では原理的に勝てないので、ここを強化するなら「知覚を変える非幾何の改変(可視ウォーターマーク等)」が必要だが、視認性とトレードオフになる
- **PoWは「壁」ではなく「コスト」**。攻撃者の計算資源をゼロにはできない
- クライアント側のシグナルは原理的に偽装可能なので、サーバー観測の項目(2,4,5,6,7)を主軸に据えている
- メモリ保持・単一プロセス前提(スケールさせるならRedis等へ)

### 残る限界: AIタグの誤り(実測で確認)

hikabooruのタグはAIが一括付与したもので、**個々の画像に対する正誤が保証されない**。
実測で次の2種類の誤りを確認した:

- **誤付与**: 電車の画像に「バッグ」、商品の箱だけの画像に「カーディガン」(正解側に混ざる)
- **誤漏れ**: カーディガンを着ている画像に「カーディガン」が付いていない(人間が選ぶと不正解になる)

一貫性フィルタと出現回数優先である程度は除けるが、**ゼロにはできない**。
完全に解くには実行時に画像を見てタグを検証する必要があり、それはビジョンモデルの常時利用が前提になる
(このプロジェクトでは方針として使っていない)。
